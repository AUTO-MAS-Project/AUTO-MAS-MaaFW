# 0.3.0 已知问题

0.3.0 是积木仓库服务化之后的第一版：三块服务插件（agent 环境、运行、项目更新）之间、三个专项（通用 MFW、M9A、MSS）与服务插件之间，只经宿主的服务调用，不再互相导入模块（契约见 [`service-contract-0.3.md`](service-contract-0.3.md)，契约文档第 10 节列了方案与代码不一致的十处，以代码为准，这里不重复）。九个包（积木仓库六个、三个专项）一起升到 0.3.0。这份清单接在 [`known-issues-0.2.0.md`](known-issues-0.2.0.md) 后面：0.2.0 的条目逐条复核过，还在的留在「清单」里（编号沿用），已经消掉的移到「已消」，新发现的从第 50 条起接着编。

**要配的宿主**：MFW 已改为插件提供、并带 0.3 服务化收尾（先封入口、停完任务再封服务注册表）的那一版及以后；宿主对三个专项的最低版本是 0.3.0。**不能与 0.2.0 混装**：0.2.0 的三个专项写的是 `>=0.2.0,<0.3`，并直接导入服务插件里 0.3.0 已经删掉的模块，0.2.0 的专项配 0.3.0 的积木、0.3.0 的专项配 0.2.0 的积木都跑不起来，九个包要一起装、一起升。

口径照旧：主路径能装能跑就交，已知问题列清单。本轮整体回归的口径是 P2 及以下的问题不挡发版。本文写于 2026-11-25 发版之前，下面的验证用的是发布前在本地构建的 wheel，按用户真实的安装方式（宿主自己用 uv 装发行包，不建指向源码的联接）装进宿主。

### 模拟器真机

在 flow-b 的 0 号模拟器上、M9A v4.15.1、《重返未来：1999》上跑，宿主非提权，九个 0.3.0 wheel 只经 find-links 提供、没建联接，模拟器无头开关。

| 场景 | 结果 |
| --- | --- |
| 成功轮 | 通过，212 秒，四个任务都完成。游戏目标占用：跑前为空、跑中被占、跑后清空；历史记录为成功，带 worker、MaaFW、项目三份日志和账号日志；后端日志没有 ERROR |
| 运行在途时停用运行积木、agent 环境、项目更新 | 通过：三次都在 0.02 秒内被拒，原因分别写明还有运行没结束、环境正被运行使用、项目目录正被运行占用；任务照常跑完 |
| 运行中手动停止 | 通过，110 秒。worker、agent、adb 子进程在停止后约 0.4 秒内全部退出；之后正常关模拟器，再交回预约；后端子进程为 0；历史为取消，日志都在 |
| 连续停止两次（先后发出） | 通过，90 秒。第二次立即返回成功，没有重复收尾的报错 |

收尾检查：每轮之后后端子进程、端口、设备占用都没有残留，模拟器每轮都由 `modavd stop` 正常关机。账号日志与 11-22 那轮（0.2.0）逐行对照，服务化本身没有让账号日志多出或少掉哪一段。第一轮漏开全局静默模式、模拟器带窗口开了机，那一轮作废，成功轮以打开静默模式后的重跑为准。

### 没做的

- Win32 控制器、终末地 PC（要提权的运行）。
- MSS 的真机（测试环境里没装星塔旅人）。
- 密码类选项的打码检查（要填密码类选项）。
- 前端界面本身：联调只走了接口，没有看界面。
- 在 PyPI 上发布后的复核（九个包还没发）。

## 在 v5.10.0-beta.1 上安装会怎样

2026-11-25 在 AUTO-MAS v5.10.0-beta.1（还没有让位给插件的内置 MFW 的宿主）上实测。

- **市场里看得到、点得了安装。** MFW 专项、M9A 专项、MSS 专项、MFW agent 环境、MFW 项目更新、MFW 运行六个包都显示出来（这次实测时目录里是 0.2.0），按钮可点；三个库不在市场里。目录来自数据站，市场不检查宿主版本。
- **装三个专项中的任何一个，都会被专项包自带的检查拒绝加载。** 整族会先解析、下载、装进插件环境，然后导入时报「当前 AUTO-MAS 仍内置 MFW / M9A / MSS，请换到让位分支」；项目更新插件在 b1 上则因宿主缺少它要的 `HealSkip` 导入失败。宿主记「无法导入插件包」，安装记录写成失败；不需要重启，失败当场返回。0.3.0 的本地 wheel 在 b1 上表现和 0.2.0 完全一样。界面只会显示泛泛的「操作失败」（这一点是读前端代码得出的，没在界面上看）。
- **重启后宿主把插件环境整体回滚**，提示「插件环境启动未完成，已保留原环境，请检查后重试」，专项那条记录一并删掉；三个服务插件会留下「未加载」的空壳记录，只影响显示。
- **在重启之前，装或卸任何插件都会被挡住**：「已有插件安装等待重启或恢复，请先重启后端完成该操作」。
- **没有丢数据。** b1 上已有内置 MaaFW / M9A / MSS 托管、账号、MSS 计划表和队列引用时，从安装、停用、启用、卸载到多次重启，`scripts.yaml`、`plans.yaml`、`queues.yaml` 前后逐字节相同，`config` 下没有多出备份目录；三条托管始终由内置实现处理，预览和状态接口照常。
- **服务插件单独装。** 运行积木 0.2.0 能装成功（连带 agent 环境与两块库），重启后要先启用 agent 环境再启用运行积木；它们对内置 MFW 没有影响。项目更新装不上（0.2.0、0.3.0 都是），重启后回滚。这一条只实测了 0.2.0 的运行积木，0.3.0 的运行积木单独装没有实测。
- **要留意的一点：** 停用或卸载专项时宿主会按类型级联删掉这一类的全部托管。这次的路径走不到这一步，因为专项根本到不了启用状态；但能挡住的只有插件包里的这段检查，宿主自己没有同名类型的防线。
- 0.3.0 的包依赖里 `auto-mas-core` 仍写 `>=5.9.0b1,<6`，所以在依赖解析阶段并不会把 b1 挡在外面，挡住它的是上面的加载期检查。
